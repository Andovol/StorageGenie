## D-A — How Documents/other gets a date

**(a) PICK: A1 — flip the category to `has_expiry=True`.**

**(b) WHY:** The flag is the single gate, and every reader already handles documents without change. The only three `has_expiry` reads in product code are all on the write path — `expiry_tracker.py:434` (`observed = _observed_date(...) if category.has_expiry else None`), `:435` (`if category.has_expiry:`), and `:609` (the manual-entry refusal). No reader gates on it: `tier_for` reads only `CATEGORIES.get(slug).tier_defaults` (`expiry_engine.py:61-63`), `compute_status` reads only accepted `EXPIRY_FIELD` assertions plus the classification slug (`expiry_engine.py:262-282`), `record_due` keys off `tier/category` (`reminders/service.py:62-67`), and chat/analytics/planning read `CLASSIFICATION_FIELD` + `EXPIRY_FIELD` generically (`chat/service.py:239-261`, `analytics/service.py:129-145`). `DOCUMENTS_TIERS` (`:130-133`) and the served `long-lead-60-30` descriptor (`descriptor.py:162-167`) already ship, and the SG-073 pinning test proves the profile round-trips (`test_plugin_expiry.py:147-152`: `tier_defaults == {"long_lead": 60, "upcoming": 30}`, `expiry_assertion is None`). One-line change, smallest mechanism (G-A7), root cause not band-aid (G-A6): the shipped windows "never fire" solely because of the flag. With one guard (see premise): the `_observed_date` proposal path must be suppressed or re-labelled for documents, because `_observed_date` proposes any bare `20xx-xx-xx` found in OCR text (`expiry_tracker.py:289-319`) stamped as `date_type: EXPIRY_DATE` (`:446`) — for a passport that is plausibly an *issue* date, which would be a fabricated expiry in exactly the blueprint's forbidden sense (`:396`).

**(c) Missed option:** A1-plus-`date_type`: flip the flag but store document dates under a new `DateType` member (e.g. `valid_until`) so all existing machinery (engine, reminders, analytics, chat) is reused byte-unchanged while the stored record stops calling a passport renewal an "expiry_date". What I checked: the `DateType` enum (`expiry_tracker.py:39-45`) has expiry/best-before/use-by/manufacture/PAO/lot-code but no validity/reminder member, and `canonical_date_type` (`:231`) plus `parse_manual_entry` (`:282`) already accept any member — so this costs one enum line, not a second date field like A2.

**(d) Riskiest unverified premise:** That no consumer treats an `EXPIRY_FIELD` value with expiry-flavoured semantics in a way that misreads for documents — e.g. `bucket_for` labels any past date `"expired"` (`expiry_engine.py:72-80`; linguistically fine for a passport, but chat/planning copy saying "expired" or "use up" was never checked), and that `DOCUMENTS_TIERS` 60/30 numbers are calibrated (the code itself declares them `DECLARED UNCALIBRATED`, `expiry_tracker.py:122-126`). If any consumer special-cases the slug or the numbers misfire, A1 ships wrong reminders, not just missing ones.

## D-B — How the app lets a user classify an item

**(a) PICK: B1 — a control on the asset detail page.**

**(b) WHY:** Everything the control needs is already on that page: the asset and its assertions are loaded (`AssetDetailPage.tsx:328-330`), the served taxonomy endpoint exists and already carries both categories as active (`assets.py:35-67`; `descriptor.py:156-167`), and `client.ts` already wraps adjacent plugin POSTs (`enterManualExpiry`, `:231-241`) so a `classify` wrapper follows the established pattern. B2 reaches only newly imported items, leaving the owner's existing catalogue unreachable — and the stage outcome (D6) is about the owner's real items. B4 drags row 15's settings editor into row 11. On the pack's concurrency question: the classify route performs no version check (`plugins.py:125-153` — no `If-Match`, unlike the asset PATCH whose concurrency label is shown at `AssetDetailPage.tsx:396`), and in my judgement (`opinion`) that is acceptable here: classification is a single-label last-writer-wins field, a stale overwrite is immediately visible and re-doable through the same control, and adding `If-Match` to a hitherto version-blind route is new mechanism for negligible stakes.

**(c) Missed option:** B1-plus-Expiry-page-entry: the pack lists only asset page, review workspace, API-only, or settings editor — it misses putting the same control on the Expiry page rows, where the date/reminder outcome actually lives and where the owner will notice a dateless document. What I checked: `client.ts` exports and the asset page's data availability; I did not read `ExpiryPage.tsx` (not in the pack's table), so I name this as a location candidate, not a designed control.

**(d) Riskiest unverified premise:** That the served taxonomy's `active` flags are a safe UI source of truth — the descriptor is hand-mirrored from `CATEGORIES` (`descriptor.py:126-131` says "every category mirrors"), so taxonomy and enforcement can drift silently, and a drifted UI would offer a category the backend rejects (or hide one it accepts).

## D-C — How reclassification keeps an existing date

**(a) PICK: C1 — skip the placeholder when an active expiry exists.**

**(b) WHY:** Today's path unconditionally destroys: `classify_asset` writes `{"status": "unknown"}` / `needs_evidence` for every dateless-category classify (`expiry_tracker.py:437-440`), and `_write_assertion` supersedes the previous active assertion on the same field (`:344-348`) — so reclassifying an item with an accepted date replaces the owner's date with a placeholder and re-opens a manual task. C1 is the minimal guard (G-A7): check `_active_assertion(db, asset.id, EXPIRY_FIELD)` first and skip *both* the placeholder branch *and* the observed-date proposal branch (`:442-450`), since a proposed OCR date would equally supersede an accepted one. C3 knowingly discards owner-entered data to save one conditional — backwards. C2 writes the same value twice for an audit trail nobody reads. C4 leaves the destructive API path intact while pretending the UI is safe.

**(c) Missed option:** The list covers only moves *between dated categories* and never the reverse move — classifying a dated item *into* `non_perishable` (or any `has_expiry=False` category): `classify_asset` touches no expiry assertion in that case (`:434-451` — the whole block is skipped), so the old accepted date stays active under a dateless classification and `compute_status` keeps reporting it. What I checked: the full `classify_asset` body plus `_active_assertion` semantics. The packet should state whether the reverse move supersedes the date, keeps it, or is refused.

**(d) Riskiest unverified premise:** That a carried-over date is semantically valid under the new category — C1 preserves bytes, not meaning. Reclassifying bleach (a `use_by` date) as a passport keeps a wrong-typed date alive with no re-prompt, which is data corruption by preservation. If category changes routinely cross that semantic boundary, C1's "keep" is as wrong as today's "erase."

## D-D — How the expiry-date form behaves

**(a) PICK: D1 — show the form for a classified category with windows; pre-fill the latest active date.**

**(b) WHY:** Two defects are evidenced, and D1 fixes both with one rule. First, the render gate blocks the entire edit path: `{expiryAssertion?.review_state === "needs_evidence" && (...)}` (`AssetDetailPage.tsx:403-405`), so an accepted date has no correction UI — contradicting the D6 outcome and the D4 opened-date precedent, where Edit pre-fills the current value (`OpenedCountdownSection.tsx:147-154`, `setValue(row.opened_date ?? "")`). Second, both finds ignore review state — `assertions.find((item) => item.field_path.endsWith("expiry_date"))` (`AssetDetailPage.tsx:330`; `ExpiryEntryForm.tsx:18`) — so with superseded rows present the form can display a dead record rather than the active plugin assertion; the engine, by contrast, reads only `accepted` (`expiry_engine.py:262-268`) or latest-active (`:119-129`). D1 (gate on classification profile's `tier_defaults`, read the active assertion, pre-fill accepted/proposed into the input, Save writes accepted) also gives proposed dates an accept path, which no other option provides. D2 keeps two UI states for one form for no behavioural gain; D3 contradicts the approved stage outcome.

**(c) Missed option:** Clear parity with D4 — the opened-date pattern the stage is told to follow ships Edit *and* Clear (`OpenedCountdownSection.tsx:155-164`, clear via null active assertion), but D1 as framed has Save only and no path back to dateless. What I checked: the full `OpenedRow` component and the `store_manual_expiry` close-out (task resolution at `expiry_tracker.py:614-625`) — a "clear date" needs a defined task/assertion end-state the list never specifies.

**(d) Riskiest unverified premise:** That the frontend's `assertions` array actually contains superseded rows — if the asset-detail API already filters to active assertions, the "wrong record" half of D1's motivation does not exist as framed, and the fix shrinks to the render gate plus pre-fill (`opinion` leaning on the pack's framing; the asset-detail read path was not in my named set).

## What would make the whole approach wrong

If the blueprint's date rule (`:396` — "Categories with no applicable expiry concept (clothing, tools, most documents) simply have no expiry assertion — the system must never force a date onto a category that doesn't logically need one") describes the owner's actual documents rather than just most documents. A1/D1/C1 then build the exact thing the blueprint forbids: date machinery that pressures keepsakes, letters, and sentimental items into carrying reminder dates, with OCR proposals auto-suggesting issue dates as expiries. In that world the correct close is A3 (documents stay dateless, 60/30 windows documented as unreachable-by-design), and this stage's "documents gain their windows" outcome is itself the error — a product-scope mistake no implementation choice can fix. Second, smaller world: if the live household holds no household/document items (last census: 1 accepted classification, `food_beverages`, zero cosmetics — `SG-240_report.md:30`), the stage ships four UI/backend behaviours with no owner data to exercise them, and the "proven live" bar the project applies elsewhere cannot be met.
