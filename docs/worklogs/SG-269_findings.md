# SG-269 findings — capture-to-find walk

Read-only walk on a throwaway copy. Method: real HTTP routes on a throwaway
backend (127.0.0.1:8011, temporary SQLite under scratch, no provider key) plus
in-process `TestClient` with the repo's `ScriptedPhase2Provider`
(`backend/tests/test_phase2_e2e.py:187`) for the AI journeys. Screen claims cite
the React source by `file:line`; no browser driver was installed and no frontend
server was started. This cannot show look, feel or layout on a phone.

Logs: `SG-269_g0.log`, `SG-269_walk.log`, `SG-269_j3j4.log`,
`SG-269_j3b.log`, `SG-269_scripts.log`.

## What a failure would have looked like (vacuity check)

- J1 would have failed if `POST /v1/assets` returned non-201, the catalog `q=Whole` missed the row, classification returned no classification assertion, the date POST returned non-200, or the Expiry status omitted the row. All five were observed (`SG-269_walk.log`).
- J2 would have failed if the import job never reached `AWAITING_REVIEW` or produced no candidate. It did both; the finding is that the candidate has no screen entry. Direct candidate read/accept was used only to continue the walk, and is labelled as such.
- J3 would have failed if the scripted provider was not invoked or the candidate did not carry the proposed date. Provider invocations `1`; date present; the finding is that the date is not accepted and is overwritten at classification.
- J4 would have failed if no task existed or the task was resolvable. Task existed; bare resolve `422`; accept `409`.
- J5 would have failed if the asset task link opened a candidate or the bare resolve succeeded. It returned `404` and `422`; the asset-page date path `200`.
- J6 would have failed if the two same-name assets did not both appear, or the same-photo import created a second asset. Both appeared; the duplicate import linked instead.
- J7 would have failed if Non-perishable did not resolve the task or still produced an unresolved row. It resolved the task and still produced a `dateless` unresolved row.
- J8 would have failed if the quantity PATCH did not persist. It persisted at version 2; the finding is the absence of a mark-gone screen.

## Limits

- Barcode-specific J6 is not established: the throwaway runtime logged
  `pyzbar/libzbar is not installed` and `tesseract is not installed`, so no
  barcode/OCR observation could be generated. The same-name and same-photo
  paths were driven.
- No browser driver (Playwright/Puppeteer) was installed. Chrome exists on the
  box, but no frontend server was authorized, so the walk used the real HTTP
  routes plus source citations, not rendered screenshots. Look, feel and phone
  layout are out of scope for this evidence.
- The scripted AI journeys use the repo's test fake, not a real provider; no
  network call, key or spend occurred.
