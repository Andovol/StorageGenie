D-F — the reverse move's task (Architect's pick: F1 — resolve the task in the move)

(a) The strongest case AGAINST F1, with evidence: the module's own doctrine says open manual tasks are sometimes real obligations, not always cleanable bookkeeping. `_orphan_manual_tasks` (`backend/app/plugins/expiry_tracker.py:641-683`) exists because a split leaves an origin's `expiry.manual_entry` task orphaned while children share the evidence, and its docstring states the rule explicitly: "A task whose origin did not share the evidence is left untouched" — i.e., open manual tasks can carry split-origin obligations that must survive. F1 resolves *all* open `expiry.manual_entry` tasks on the reverse-moved asset, yet the same task type is also opened for evidence review rather than date entry: `apply_extraction_result` (`expiry_tracker.py:414-425`) opens the identical `expiry.manual_entry` task via `_manual_task` when extraction carries `needs_evidence`. A reverse move on such an asset would silently drop evidence-review work under F1. There is also a contract-shape cost with evidence: `store_manual_expiry` returns the resolved list and the route reports `resolved_review_task_ids` (`plugins.py:221-225`), while the classify route returns a single `review_task` id-or-None (`plugins.py:150-160`); the reverse branch currently returns `task=None` (`expiry_tracker.py:481-485`). F1 therefore either resolves tasks silently (an auditability gap — resolutions without a reported id, unlike both siblings) or changes the classify response shape. F3 (block the move while a manual task is open) preserves the invariant, evidenced by both siblings, that every resolution follows a deliberate user date action (entry or clear, `expiry_tracker.py:626-637`, `698-709`) — a classification move is not a date action — and forces explicit triage instead of silent cleanup.

(b) A premise of F1 that is unverified: that an open `expiry.manual_entry` task on a reverse-moved asset is always meaningless. The audit verified only that the two *expiry* routes 422 on `non_perishable` (`expiry_tracker.py:616-619`, `693-694`); it did not establish that the task is otherwise unresolvable — a generic resolve exists (`resolveReviewTask`, `frontend/src/api/client.ts:223-229`, `POST /v1/review-tasks/{id}/resolve`), whose guards on this task type were not in evidence. If the inbox can resolve it, the "limbo" finding overstates Entrapment: the task is resolvable, just not from the expiry surface.

(c) The observation that would settle it: (1) read the `POST /v1/review-tasks/{id}/resolve` route and its guards — if it accepts `expiry.manual_entry`, the limbo is a surface gap, not a trap, and F1's urgency drops; (2) enumerate every producer of `expiry.manual_entry` (classify placeholder at line 470, extraction at line 425, split orphans via lines 641-683) and test the disputed case directly: seed an asset whose open task comes from extraction `needs_evidence` (not a missing date), reverse-move it under F1 semantics, and check whether evidence-review work is dropped.
