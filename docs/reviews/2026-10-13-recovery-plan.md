This is the recommendation owner requested, prepared during the approved full-app audit. It is **Architect judgement**, pending SG-180/181/182 evidence and final reconciliation. Canonical evidence/status is `2026-10-13-recovery-audit.md`; scenario definitions are `2026-10-13-user-scenarios.md`. This document owns proposed repair order and user-facing design outcomes, not defect status, runtime counts or completion percentages. No calendar/cost promise is measured.

## Recommendation — complete the existing journeys and unify the existing UI

The audited code already has catalog/search, capture/import jobs, candidate review, assertions/history, expiry, lifecycle/location/relation APIs, planning/chat/analytics and evidence/export/recovery mechanisms. Their presence does not mean the full journeys work: task/blocker projection, classification/Resolve/visibility, CREATED-job action, silent API errors, responsive layout and verification limits are separately recorded in the canonical register. Preserve actual capabilities and accepted deferrals, replace disconnected actions and inconsistent page structure rather than begin an unbounded rewrite.

| Approach | Gives | Costs / limits | Recommendation |
|---|---|---|---|
| Existing CSS/component repairs only | Smallest changes to overflow/contrast and known blockers | Does not by itself unify navigation, task completion, missing controls or Settings discoverability | Use for independent reversible root-cause repairs inside a coherent plan |
| Reuse existing shell/components/tokens; complete real user journeys | One navigation/context system; consistent states; existing API/provenance retained | Some route composition/form/flow work; explicit scope/acceptance needed | **Recommended**, judgement: matches current reusable assets and actual journey gaps |
| Whole-app framework/UI/domain rewrite | Freedom to replace structure | Recreates already-existing behavior, evidence lineage and controls; broad migration/regression and permissions burden | Not justified by current audit evidence |

This plan replaces another competing phase checklist with linked scenarios, canonical findings and small outcome-based slices. It adds no service, watcher or approval gate. Existing story/spec/decision documents remain evidence owners; do not copy them into a second requirements system.

## Concrete modern UI outcomes

| Surface | Proposed outcome | Existing reuse / proof |
|---|---|---|
| Navigation and page context | One shared shell with persistent household context, active destination, primary capture/add action and discoverable Inbox/task status; narrow layout uses an accessible menu with all destinations reachable | Existing AppShell/AppHeader/Nav/tokens. Avoid clipping or hiding focusable links as a cosmetic fix. Final information grouping is a design judgement, not accepted owner taxonomy |
| Catalog/search | Responsive toolbar; search/filter/sort clearly describes whole-catalog versus loaded items; cards/table have consistent density and evidence/provenance affordances; loading, empty result and API failure distinct | Existing CatalogToolbar/ProductGrid/ProductCard and query hooks; actual multi-page/saved-search semantics first |
| Capture/processing | Accepted formats/limits visible; readable upload error; one deliberate processing action, durable progress/retry/recovery; drafts preserved through failures and navigation where existing scope allows | Existing upload/import modal/jobs pipeline; no fake progress or backend state relabel |
| Review/expiry/tasks | Fields and source evidence side by side when space permits, stacked on narrow screens; clear uncertainty/Unknown and blocker explanation with the actual completing action; pending mutations give understandable feedback | CandidateCard/ReviewPage/ExpiryEntryForm/task routes; current review grid/blocked labels are evidence, not finished workflow |
| Detail/history | Editable values, classification/date/lifecycle controls and history/source evidence are distinguishable; disabled location/relation capability is not confused with data absence | Existing AssetDetailPage/AssertionHistory/EvidenceGallery and actual feature state; taxonomy fallback remains rejected |
| Agent pages | Shared page hierarchy/controls; trust/input/source/consent/cost and explicit confirm/dismiss/correct states, understandable provider/error/empty state | Existing planning/chat/analytics routes; no claims about live intelligence from a fake provider |
| Settings/recovery | Group only in-scope household/config/privacy/export/recovery functions that already exist or receive explicit implementation approval; avoid advertising a connection/settings function absent from this screen | Settings model/reset current UI versus backend/export/operator capabilities; user remains zero-command operator |
| Visual consistency | Existing type/spacing/color/radius components apply across pages; readable secondary text, consistent form validation and pending/error feedback; modern appearance assessed with the actual design review, not a subjective score passed as fact | Existing theme tokens/components; muted-text pair defect is measured, aesthetics remain judgement |

Accessibility acceptance sources are primary W3C guidance: [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [target size with spacing/exception semantics](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum). Non-excepted horizontal-language content is assessed at 320 CSS px for reflow; normal text contrast uses the applicable criterion rather than an invented threshold. No current certification: SG-183 observed 390/834/1440 desktop-rendering widths, sampled targets and opaque contrast; normal Tab/zoom/touch/320/authenticated URL/complex opacity remain explicit proof limits. Future checks use actual native behavior, not preventScroll-induced failure or a true/true control.

## Workable-state definition and final reconciliation

Architect judgement: a workable recovery completes the primary capture→review→catalog→expiry/task journeys for initial/returning households, retains evidence and correction history, prevents wrong-household/replay/rollback defects actually established by audit, provides honest recoverable failures, and supports the same scoped outcomes on narrow/wide keyboard-accessible screens. Secondary capabilities have explicit supported/deferred/unverified dispositions, no misleading button or empty-state claim. Production acceptance also needs actual authorized release/build/schema/data readback; a source test or loopback-rendering screenshot cannot substitute for it.

The requested session close occurs after audit reconciliation; the standing deploy obligation remains blocked by held code unless safely authorized and discharged. No new close-time approval question is manufactured. Exact blocked item and next-session decision will be recorded in final handoff/RESUME, with paste-ready starter.
