# StorageGenie user scenarios — reproducible audit and recovery acceptance cases

These are Architect-authored test scenarios derived from the blueprint journeys A–H and UX/security sections, accepted optimizations, approved Phase 3 and ingest/enrichment specifications, and RECOVERY-D1/D2. They are proposed acceptance cases within existing intent, not additional owner-approved implementation requirements. Unresolved product scope remains a decision in the final recovery proposal.

The canonical story IDs and coverage/status are owned by `2026-10-13-recovery-audit.md`. This document owns how to exercise them. It carries no duplicate current pass/fail table. Current actual evidence and gaps are linked from the canonical register and per-slice audits. A screen rendering is not completion of a writable story; every applicable write requires real writer → persisted value → reader proof.

## Common execution boundaries

Existing deployed household/item observations are GET-only. All mutation, failure/retry, concurrent edits, imported files and synthetic provider output use explicitly disposable DB + evidence roots and dependency overrides before the first write. No production keys/settings copied. Scripted providers exercise contracts and failure handling; they do not prove live provider quality. No paid call, auth/config/permission change, restart or production repair is implied. Preserve prior decisions: manual planning first, in-app reminders before push, no asset_type fallback for grounded chat, scene UI separately parked.

## Scenarios

| Scenario / story | Setup and user action | Observable completion | Negative / recovery case |
|---|---|---|---|
| SC-01 / REC-ST01 | Returning household member opens the app and selects their household; separately start a disposable empty catalog and simulate an API outage. | The selected catalog and navigation context remain consistent; onboarding or empty state gives a usable next action without developer commands. | Auth/network/server failure is shown as failure, not as zero households/items. Household selection is not treated as authentication. |
| SC-02 / REC-ST02 | Capture a camera photo or choose a supported photo/document; stage several files including a rejected type/oversized/damaged input. Submit accepted inputs. | Accepted/rejected files and reasons are visible; source evidence preserved; job progress/errors and resulting candidates are reachable. | Rejection does not silently drop files; a later upload failure allows understandable retry/cancel without duplicate imports or orphaned state hidden from the user. File support is reconciled between Capture/import and the actual backend contract. |
| SC-03 / REC-ST03 | Uncheck auto-detect, create an import, open its CREATED job in Inbox, then choose to start it. Compare checked immediate-run and FAILED Retry paths. | The promised start action reaches the existing runner; it advances the real job and exposes resulting review candidates. | No Run action is a disconnected user transition even when the backend /run works. Repeat/start/retry must not create duplicates or launch simultaneous uncontrolled work. |
| SC-04 / REC-ST04 | Review an uncertain candidate beside its evidence. Exercise edit/accept/hold/reject, duplicate suggestion, multi-item split and supported merge flow in disposable data. | Current blockers and their completion actions are clear; accepted fields preserve evidence/provenance and produce a readable asset; split/merge retains lineage. | Open tasks block both click and shortcut; resolving through the real writer refreshes the response; stale stored task IDs do not block. Pending actions do not duplicate writes. Unknown remains available, and rejected/held states are truthful. |
| SC-05 / REC-ST05 | Seed a multi-page disposable catalog, search/filter/sort it, move between pages, save/reopen/delete a search and navigate to an item/back. | Results and counts match the selected household/query; declared page-local or global sorting is honest; saved search restores meaningful state. | No matches, invalid/stale search, deleted saved search, request failure and incomplete page must not be confused. Current loaded count is not presented as household total. |
| SC-06 / REC-ST06 | Open an item, inspect provenance/evidence, correct a field and attach another valid source; reload detail and history. | Real updates persist with accepted source, previous assertion superseded and history/evidence visible; original evidence bytes unchanged. | Foreign evidence, failed upload, conflicting correction and missing thumbnail yield explicit outcomes; fallback remains useful without claiming a successful photo load. |
| SC-07 / REC-ST07 | Record supported lifecycle transitions, assign/unassign a location and create/remove a typed relationship where effective flags permit them. | Domain rules, household boundaries, timestamps/history and readback agree; dormant features are identified as dormant, not absent. | Illegal lifecycle transitions, cycles, cross-household relationships, stale versions and disabled capabilities are rejected or explained. Historical events are not rewritten to make the latest state look plausible. |
| SC-08 / REC-ST08 | Accept an expiry-relevant item, classify it through an actual user control and enter a missing date with evidence. Also use a non-perishable item. | Classification and accepted date/type/source persist; intended task completes; non-applicable expiry stays distinct from unknown/unresolved. | Classification missing or invalid date produces actionable validation, not a dead-end or invented date. Assert readback and task completion together. |
| SC-09 / REC-ST09 | Open attention/expiry views containing urgent, future, unknown and unclassified items; follow each task type's action to completion. | Urgency ordering is correct for the execution clock; every task reaches the correct asset/candidate/form; unresolved items remain visible with meaningful next action. | Bare Resolve must not erase data-required work. Empty streams cannot falsely imply all items are safe. Do not rewrite previously verified ordering without a discriminating failure. |
| SC-10 / REC-ST10 | Trigger planning manually against confirmed label/catalog fixtures, then confirm/dismiss a proposal and reload. | Suggestions remain proposals until explicit confirmation; backing item/label facts, uncertainty and recorded provider accounting are accessible. | Missing classification/label data, consent off, provider failure and no applicable items produce honest outcomes. No autonomous execution or unsupported safety/medical certification. |
| SC-11 / REC-ST11 | Ask a category question against accepted household classification fixtures, inspect cited owned-item evidence and record a correction. | Grounding stays within selected household/category and trusted facts; uncertainty/correction is clear. | Empty or unclassified inventory, stale classification, provider failure and unsupported inference must not silently fall back to unreviewed asset_type. Session-only chat versus durable history is explicit. |
| SC-12 / REC-ST12 | Request source-grounded enrichment in scripted fixtures; review exact/fuzzy identity proposals and conflicting photo/web values; accept through actual available controls. | Sources, retrieval/snapshot lineage and acceptance/readback are preserved; label-visible evidence precedence is enforced; discarded proposals are not facts. | No source, wrong product, conflicting field, malformed response and transport failure are visible; per-field UI gaps are recorded rather than hidden by candidate-wide API success. No live metered call in audit. |
| SC-13 / REC-ST13 | Inspect analytics for empty, mixed-category, dateless and lifecycle fixtures; compare chart/summary inputs with source rows. | Structured numbers, denominator and time window are understandable; generated insight is clearly separate and grounded in those inputs. | Uncategorized/missing data is not silently dropped; an empty or failed query does not look like a measured zero; scripted generation is not live model evaluation. |
| SC-14 / REC-ST14 | Inspect settings and actual privacy/model choices; export a disposable catalog/evidence manifest, restore it into a different disposable destination, then verify readback. | Available controls are honest about persistence/effective state; complete portable evidence + DB relationships can be recovered; source schema/version is identified. | Restart-reset model choice is disclosed; unsupported configuration controls are scope gaps. Interrupted restore, missing/corrupt evidence and inconsistent manifest fail visibly without touching live storage. |
| SC-15 / REC-ST15 | Traverse every route, navigation/dialog/drawer and main flow on narrow/tablet/desktop layouts; keyboard through focus and relevant states. | Requested device/layout/visual viewport and component sizes are separately recorded; labels/actions/evidence remain visible and usable; focus is visibly within the viewport. | Deliberate overflow and API-failure controls discriminate real defects; clipped or expanded mobile layout is not reported clean. WCAG contrast/target-size claims include actual colors, spacing and exceptions, not threshold-only guesses. |

## Cross-cutting technical acceptance questions

| Case ID | Question to prove with a real boundary |
|---|---|
| CX-01 | Same input/key/retry gives intended idempotent result; another household or a changed request cannot reuse a foreign response. |
| CX-02 | Every reader checks ownership of its subject and linked evidence; configured ingress protection and query scoping have distinct roles. |
| CX-03 | A partial failure rolls back the intended atomic unit or leaves a documented resumable state with no silent data loss. |
| CX-04 | Every AI-derived assertion traces provider/model/prompt/input/output/acceptance/accounting without exposing keys or treating OCR text as trusted instructions. |
| CX-05 | Original/derivative paths, media signatures, image limits, EXIF and file serving protect evidence and private data; same-size content corruption defeats a names/sizes-only check. |
| CX-06 | Tests drive actual writers/readers and failure paths; full coverage claims are scoped to executed tests, builds and real deployed observations. |
| CX-07 | Build/migration/backup/restore and rollback procedures are executable in their declared environment; no fragile interpreter/path assumption is called a product failure. |
| CX-08 | Every gap is labeled broken/partial/absent/dormant/deferred/unverified with evidence scope, severity as judgement, dependency and smallest viable repair; no new feature is accepted by accident. |
