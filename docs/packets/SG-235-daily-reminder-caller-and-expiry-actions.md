## Why this exists

SG-233 built the reminder store, the real-engine writer `record_due`, and the in-app sender (the `GET /v1/reminders` list plus the read/dismiss transitions), and SG-234 served it. **Nothing calls the writer.** The live database still holds `reminder` = 0 rows, because a row only exists once somebody runs `record_due` for a day — and no one does. The Expiry page therefore renders `Unread reminders (0)` forever, and the owner has no way to act on a reminder either: the read/dismiss endpoints exist and the client wrappers exist, but the page shows no buttons (SG-233's own report: *"no UI read/dismiss buttons (wrappers only, not asked)"*).

This slice closes both gaps with the smallest mechanism that can: **one background task inside the app** that runs the existing writer for every household once at startup and then every 24 hours (UTC), and **two buttons on the Expiry page** that call the endpoints SG-233 already shipped. No new table, no migration, no email, no host cron, no new dependency.

## G1 — the daily caller (a background task inside the app)

- **One module** inside the existing package `backend/app/services/reminders/` (e.g. `daily.py`; name it this or report why the name differs) exposing two units — the names are yours, the **properties below are not**:
  - a **pass**: run one daily pass over EVERY household and return a result the caller can read (households visited, reminders created, errors) — it opens its OWN session (the session factory is a parameter, not a module global), calls `record_due(session, household.id, today)` for each household, and closes the session. **It must never be a re-implementation of `record_due`:** the production writer stays `app.services.reminders.service.record_due`.
  - a **loop**: run the pass once immediately, then every **24 hours (86400 s)**, and stop promptly when cancelled.
- **Cadence.** The interval is measured from the previous pass; it is **not** re-aligned to midnight. The shipped default is 86400 s and it is a **constant of this feature** (the owner's decision says 24 hours) — no new setting, no new env var, no compose change.
- **The current UTC day only.** Each pass computes the day read from the live clock at execution (`datetime.now(timezone.utc)`), never a fixed date and never a stored "last run" day. **No backfill:** a pass NEVER walks missed days, and there is no catch-up pass. If the process was down for three days, the next pass computes **today only** and the two missed days produce **no rows** — that is a required behaviour, not an edge case.
- **Every household.** The pass enumerates the whole `household` table, including households with no due assets (they are visited and produce zero rows).
- **One household's failure does not stop the rest.** An error raised while handling one household is recorded (in the result and in the log) and the pass continues with the next household; the pass itself returns normally. The loop survives a failed pass and keeps its cadence.
- **The app keeps serving.** The pass runs **off the event loop** (the app answers `/v1/health` while a pass runs). A pass that blocks the event loop would stall the container's healthcheck (`interval: 10s`, `retries: 5`) and can trigger a restart loop.
- **Clean shutdown.** When the app shuts down, the task is cancelled and the app stops promptly — state the bound you implement and prove it (the container must not hang until the runtime kills it).
- **Startup wiring — the served app starts the pass exactly once.** The expected shape (decide and report if you find a better one): a small served-entrypoint module that attaches the lifespan to the **same** app object (so every route, the middleware and the static serving are unchanged), plus the one-line `CMD` change in `backend/Dockerfile` to serve that entrypoint. The alternative shape — a pytest-inert guard inside `backend/app/main.py` — is acceptable **if you prove the inertness with a test** (see G2). **Not acceptable:** a pass that starts whenever `app.main` is imported; a shape that needs a new environment variable, a new compose key or any host-side configuration (the served container must run the daily pass with **zero** new configuration).
- **Safety — no test may write outside its own temp database.** The `SessionLocal` engine is bound at import time to `settings.database_url`; under the canonical test command (`cd backend && python -m pytest -q`, see `Makefile`) the default relative path resolves to `backend/data/db/storagegenie.db` — a file the test environment must never create. The production container's URL is absolute (`sqlite:////data/db/storagegenie.db`). Therefore: the test suite must start **no** daily pass, and the relative default path must never be created. The daily pass takes its session factory as a parameter precisely so a test can hand it a temp factory.
- **Idempotence.** A second pass on the same UTC day creates **zero** new rows — structural in `record_due` (unique `(asset_id, as_of_day)`), and proven **through the new caller**, not only through `record_due` directly.
- **No schema change.** The `reminder` table and its unique guard already exist (SG-233). **No migration, no model change, no `config.py` change** — enumerate the current alembic heads in-slice and quote them; the packet's expectation is that no new revision is needed (a difference is a finding, not an obstacle).
- **While you are in `backend/app/main.py`:** the reminders router is registered through an inline `__import__("app.api.v1.reminders", fromlist=["router"]).router` (line 83). Normalize it to an ordinary top-level import beside the other routers (SG-233's audit left this for the next touching slice). **No behaviour change.**
- **Nothing else changes** in the backend: `backend/app/api/v1/reminders.py`, `backend/app/models/*`, `backend/app/db.py`, `backend/app/config.py` and `backend/app/services/expiry_engine.py` are outside the ceiling.
